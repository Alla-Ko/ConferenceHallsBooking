# Документація проєкту

API для пошуку конференц-залів, бронювання, розрахунку оренди за часом доби та звітів. У ТЗ були зали, додаткові послуги, пошук, бронювання і ціна. Нижче також правила, яких **не було в ТЗ**, але які запроваджені в проєкті.

## Що додано понад ТЗ

- **Користувачі і ролі.** Register / login / JWT. Ролі `User` і `Admin`. Запис у каталог — лише Admin; бронювання — лише автентифікований користувач. Адмін теж може створювати бронювання.
- **Бронювання як заявка, а не миттєва бронь.** Нова заявка має статус `Pending`. Слот зайнятий лише після того, як адмін поставить `Confirmed`.
- **Немає редагування і видалення** бронювань. Щоб змінити заявку: скасувати/відхилити і створити нову.
- **Лише цілі години**, один календарний день, вікно **06:00–23:00** (годинник користувача, UTC+3). Без нічних броней і без хвилин (немає 10:17). Інтервал напіввідкритий: `[start, end)` — `10:00–14:00` і `14:00–16:00` не перетинаються.
- **У БД час у UTC.** Клієнт шле дату і години в UTC+3; API конвертує в UTC для збереження і порівнянь.
- **Знімок ціни** при створенні, але **Confirm перераховує** за поточним тарифом залу і поточними цінами послуг. Розбіжність → автоматично `Rejected` (`Price mismatch`). Послугу прибрали із залу → автоматично `Rejected`. Інші перетинні `Pending` → автоматично `Rejected` (`Time slot is occupied`). Confirm іде в **транзакції**.
- **Звіти** для Admin (виручка, завантаженість, клієнти).

## Ціноутворення

Оренда залу — **за годину**. Додаткові послуги — **один раз на бронювання**, не за годину.

| Години користувача (UTC+3) | Правило                                            |
| -------------------------- | -------------------------------------------------- |
| 12:00–14:00                | Пік, +15% (ці години **не** рахуються як стандарт) |
| 06:00–09:00                | Ранок, −10%                                        |
| 18:00–23:00                | Вечір, −20%                                        |
| 09:00–12:00 і 14:00–18:00  | Стандарт (базовий погодинний тариф)                |

Приклад: 10:00–14:00 = 2 стандартні години + 2 пікові.

## Бронювання

Статуси: `Pending`, `Confirmed`, `Rejected`, `Cancelled`.

- Слот **зайнятий**, лише якщо є `Confirmed` з перетином `[StartAt, EndAt)`.
- `Pending` не блокує пошук і інші заявки.
- Послуги в заявці мають належати цьому залу. Порожній список дозволений.
- У заявці на бронювання поля місткості немає — її не передають і не валідують. Максимальну місткість залу користувач може бачити в пошуку (capacity) і задати відповідний фільтр, але це не заважатиме йому після цього обрати зал з меншою кількістю і забронювати його.
- Старт у минулому відхиляється.
- Час початку > часу завершення бронювання відхиляється
- Час поза рамками 06 і 23 відхиляється

## Пошук

`GET /api/ConferenceHalls/available` — без авторизації.

Фільтри: зал `IsActive`, `Capacity >=` запиту, немає перетину з **Confirmed**.

Дата в query: `yyyy-MM-dd`. Години: цілі числа, UTC+3.

## Зали і послуги

- Послуги залу — many-to-many із глобальним каталогом.
- PUT залу **частковий**: пропущені поля не змінюються. `"serviceIds": []` очищає послуги; якщо `serviceIds` немає — список лишається без змін.
- Видалення послуги з каталогу прибирає її із залів (cascade на join-таблиці). У бронюваннях лишається історичний знімок назви і ціни (без FK на каталог).

## Сід (якщо таблиці порожні)

Зали A / B / C (50 / 100 / 30 осіб, 2000 / 3500 / 1500 грн/год). Послуги: проєктор 500, Wi-Fi 300, звук 700 — усі прив’язані до кожного із цих трьох залів.

## Звіти (Admin)

Усі звіти: `GET`, роль **Admin**, query `from` і `to` (`yyyy-MM-dd`), **обидві дати включно**. У розрахунок ідуть лише бронювання зі статусом `Confirmed`, у яких **час старту** потрапляє в період. Суми беруться зі знімків ціни на бронюванні, не з поточних тарифів каталогу. Вихідні рахуються як звичайні дні.

Приклад: `GET /api/Reports/revenue/halls?from=2026-08-01&to=2026-08-31`

### Виручка по залах

`GET /api/Reports/revenue/halls`

Скільки грошей приніс кожен зал за період. У відповіді є **усі зали** (навіть ті, що не орендувалися в цей період). По кожному залу: виручка за оренду, за додаткові послуги і разом. Наприкінці — підсумки по всіх залах (`totalRentalRevenue`, `totalServicesRevenue`, `totalRevenue`).

### Виручка по послугах

`GET /api/Reports/revenue/services`

Які додаткові послуги замовляли і скільки вони принесли. У списку лише послуги, які реально були в confirmed-заявках (історична назва зі знімка). По кожній: скільки разів замовили (`timesBooked`) і сума (`revenue`). Сортування: виручка за спаданням. `totalRevenue` — сума по всіх послугах.

### Оренда за часом доби

`GET /api/Reports/revenue/hours`

Скільки годин і грошей припало на ранок / пік / вечір / стандарт **по кожному залу** (лише оренда залу, без послуг). По кожному поясу: `hours` і `revenue`. `totalRentalRevenue` — сума чотирьох поясів. Усі зали в списку, навіть ті, що простоювали без підтверджених броней.

Пояси ті самі, що в ціноутворенні: ранок 06–09 (−10%), пік 12–14 (+15%), вечір 18–23 (−20%), стандарт 09–12 і 14–18.

### Завантаженість залів

`GET /api/Reports/utilization`

Наскільки зал був зайнятий у періоді. Доступних годин на день = **17** (06:00–23:00). `availableHours` = кількість днів у періоді × 17 (однакова для всіх залів). По кожному залу: підтверджені години (`confirmedHours`) і відсоток зайнятості (`occupancyPercent`). У шапці звіту також `daysInPeriod` і `bookableHoursPerDay`.

### Клієнти

`GET /api/Reports/users`

Хто бронював і скільки заплатив. У списку лише користувачі з хоча б одним `Confirmed` у періоді. По кожному: ПІБ, email, кількість броней, кількість підтверджених годин, виручка за оренду / послуги / разом. Сортування: `totalRevenue` за спаданням.

## Контролери

| Контролер         | Призначення                            |
| ----------------- | -------------------------------------- |
| `Auth`            | Реєстрація, логін, поточний користувач |
| `HallServices`    | Каталог додаткових послуг              |
| `ConferenceHalls` | CRUD залів + пошук вільних             |
| `Bookings`        | Заявка, список, зміна статусу          |
| `Reports`         | Аналітика для адміна                   |

Swagger UI: **http://localhost:5070/swagger/index.html**

Authorize → вставити JWT **без** префікса `Bearer`.

### Гість (без токена)

- Register, login
- Список послуг, список залів, зал за id
- Пошук вільних залів

### User (JWT, роль User)

Типовий flow:

1. `POST /api/Auth/login` → токен
2. `GET /api/ConferenceHalls/available?date=&startHour=&endHour=&capacity=`
3. `POST /api/Bookings` (id залу, дата, години, опційно `serviceIds`) — статус `Pending`, у відповіді розрахований total
4. `GET /api/Bookings` — **лише свої** заявки
5. `PATCH /api/Bookings/{id}/status` з `{ "status": "Cancelled" }` — лише свої `Pending`

User не може підтверджувати, відхиляти чи бачити чужі заявки. User не змінює зали й каталог послуг.

### Admin (JWT, роль Admin)

Усе, що може User, плюс:

- CRUD послуг і залів
- `GET /api/Bookings` — **усі** заявки
- `PATCH /api/Bookings/{id}/status`: `Confirmed` / `Rejected` / `Cancelled`
- Звіти `/api/Reports/...`

Flow адміна: відкрити pending → `Confirmed` (слот зайнято, перетинні pending автоматично відхиляються) або `Rejected` / `Cancelled`. Якщо з моменту заявки змінилися ціни чи послуги залу, Confirm сам відхилить заявку з `message` — без подвійної броні і без застарілої ціни.

## Основні ендпоінти

- `POST /api/Auth/register`, `POST /api/Auth/login`, `GET /api/Auth/me`
- `GET|POST|PUT|DELETE /api/HallServices` (запис: Admin)
- `GET /api/ConferenceHalls`, `GET /api/ConferenceHalls/available`, `GET|POST|PUT|DELETE /api/ConferenceHalls/{id}` (запис: Admin)
- `GET|POST /api/Bookings`, `GET /api/Bookings/{id}`, `PATCH /api/Bookings/{id}/status`
- `GET /api/Reports/revenue/halls`, `GET /api/Reports/revenue/services`, `GET /api/Reports/revenue/hours`
- `GET /api/Reports/utilization`, `GET /api/Reports/users`
